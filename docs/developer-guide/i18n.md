# Internationalization (next-intl)

The web app reads its user-facing copy from [`apps/web/messages/en.json`](../../apps/web/messages/en.json) through [next-intl](https://next-intl-docs.vercel.app/) 3.x. Only `en` exists today, but moving strings out of JSX now means adding a locale later is a translation job, not a code change. Surfaces are migrated one PR at a time; this page is the pattern each PR follows.

Worked examples:

- #872: `Navbar` and `OnboardingTour`, the original proof of concept.
- #1037 (issue #876): the dashboard and marketplace pages ([`app/dashboard/page.tsx`](../../apps/web/app/dashboard/page.tsx), [`app/marketplace/page.tsx`](../../apps/web/app/marketplace/page.tsx)), covering ICU placeholders, rich text, empty states and attribute strings.

## How it is wired

| Piece                                                                                     | Role                                                                                                                  |
| ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| [`i18n/request.ts`](../../apps/web/i18n/request.ts)                                       | Request config: fixed `en` locale, loads `messages/en.json`. Used by server components (`getTranslations`).           |
| [`i18n/locales.json`](../../apps/web/i18n/locales.json)                                   | Source locale and the list of supported locales. The completeness checker uses this as the source of truth.           |
| [`app/layout.tsx`](../../apps/web/app/layout.tsx)                                         | Wraps the app in `NextIntlClientProvider` with **the whole** `en.json`, so a new namespace needs no provider changes. |
| [`messages/en.json`](../../apps/web/messages/en.json)                                     | One top-level namespace per component or page.                                                                        |
| [`messages/en.test.ts`](../../apps/web/messages/en.test.ts)                               | Checks every key a migrated file uses exists in `en.json`, and that its namespace has no unused keys.                 |
| [`scripts/check-translations.mjs`](../../apps/web/scripts/check-translations.mjs)         | Compares every supported locale with the source catalog: keys, nested paths and ICU placeholders.                     |
| [`test-utils/renderWithProviders.tsx`](../../apps/web/test-utils/renderWithProviders.tsx) | Test wrapper with React Query and the real `en` messages. A missing key throws instead of rendering the key path.     |

Typed messages (a `global.d.ts` augmenting `IntlMessages`) are not configured, so a wrong key does not fail `tsc`. `messages/en.test.ts` covers that gap.

## Translation completeness check

`scripts/check-translations.mjs` is a dependency-free Node script that compares every catalog listed in `i18n/locales.json` with the source locale:

```bash
pnpm --filter web check:translations
pnpm --filter web test:translations
```

The first command checks the real catalogs; the second runs the checker's built-in fixtures for a complete catalog, a missing key, an extra key, a missing placeholder, an unexpected placeholder and a malformed message. CI runs both before typechecking, so a pull request fails when:

- a supported locale file is missing, or a `messages/*.json` file is not listed in `supportedLocales`;
- a nested key is missing from, or extra in, a target locale;
- an ICU placeholder such as `{name}` or `{count}` is missing or unexpected in a target message;
- a message has malformed braces, an unknown argument type, or a plural/select without an `other` branch.

The checker ignores ICU-quoted literals such as `'{name}'` and understands nested plural/select branches. To add a locale, add `messages/<locale>.json`, list the locale in `i18n/locales.json`, and run the check. Machine-translated copy still needs a human reviewer; the checker only guarantees structural completeness.

## Migrating a surface

1. **Add a namespace** to `en.json` named after the component or page in PascalCase (`Navbar`, `Dashboard`, `Marketplace`). Put it before `Common`, and keep keys in the order they render.
2. **Use semantic, nested keys**, not the English text: `header.title`, `checklist.registerProfile.status`, `invoices.emptyState.action`. Group related strings (`header`, `filters`, `emptyState`, `console`) the way the UI groups them.
3. **Copy the English exactly**, with the same punctuation, capitalization, ellipses (`...` vs `…`) and spacing. JSX collapses a multi-line text node into single spaces, so the `en.json` value is the one-line sentence the browser shows. Keep existing typos and odd copy as they are; fixing wording belongs in a separate PR.
4. **Read the strings:**
   - Client components (`"use client"`): `const t = useTranslations("Dashboard")`, then `t("header.title")`.
   - Server components: `const t = await getTranslations("Namespace")` from `next-intl/server` (sync `useTranslations` also works in a non-async server component).
   - Prefer string-literal keys (`t("filters.status.options.listed")`) over template keys (``t(`nav.${key}`)``). The key-coverage test can only check literals.
5. **Dynamic values use ICU placeholders**, never concatenation: `"Available Invoices ({count})"` with `t("invoices.title", { count })`. A plain `{value}` is inserted with `String(value)`, so numbers render exactly as the old template literal did. Keep number, date and currency formatting (`formatAmount`, `toFixed`, `toLocaleDateString`) in code, unchanged, and pass the formatted string as the value.
6. **Plurals:** use ICU `plural` only where the UI already changes wording by count (e.g. `{count, plural, one {# day} other {# days}}`). If the UI doesn't pluralize today, keep its exact output and note the plural as a follow-up.
7. **Sentences with links or emphasis stay whole.** Use `t.rich` with a tag in the message rather than splitting the sentence into fragments:

   ```json
   "body": "... Go to the <link>[Profile Page]</link> to register."
   ```

   ```tsx
   {
     t.rich("verificationBanner.body", {
       link: (chunks) => <Link href="/profile">{chunks}</Link>,
     });
   }
   ```

8. **What to extract:** visible text, button and link labels, headings, empty states, `placeholder`, `aria-label`, `title`, `alt`, and copy passed to child components as props (e.g. `emptyStateTitle`).
   **What not to extract:** console/log messages, `data-testid`s, class names, route paths, analytics event names, enum/option `value`s, API data (addresses, raw event types), and glyphs such as `!` or `—`.
9. **Page metadata** (`metadata` / `generateMetadata`) has not been migrated yet. Every route still uses static `metadata`, and the unused `Metadata` namespace in `en.json` is left over from the scaffolding. Migrate the root layout and all route layouts together in one PR (see the checklist below).

## Tests

- Render components with `renderWithProviders` (or wrap in `IntlTestProvider`) from `test-utils/renderWithProviders.tsx`. Any test that renders a migrated component without it fails with "context from `NextIntlClientProvider` was not found".
- Keep asserting on the English text (`getByText("Min Value")`). Since the values are unchanged, existing queries keep working and double as regression checks on the copy.
- Add a render test asserting the key strings and that no raw key appears, e.g. `expect(container.textContent).not.toMatch(/\bDashboard\.[a-zA-Z]/)`. See [`app/dashboard/page.i18n.test.tsx`](../../apps/web/app/dashboard/page.i18n.test.tsx).
- Add the migrated file to `MIGRATED_FILES` in `messages/en.test.ts`.

## Proving "no behavior change"

A migration PR should change where the strings live, not what users see. Before editing, render the surface in each state it has (disconnected, empty, loaded, selected, dialogs open, and so on) and save `container.innerHTML` to files outside the repo. Then migrate, render the same states again and `diff -r` the two directories. The output should be byte-identical, which covers attributes like `title`, `aria-label` and `placeholder` as well as text. For server-rendered routes you can also `curl` the page from `next start` before and after, strip scripts and React's `<!-- -->` text separators, and compare. Don't commit the throwaway snapshot harness.
